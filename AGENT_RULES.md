# Agent Rules for SIH 2026 Project 26051

This repository uses AI agents for development. All AI agents MUST strictly adhere to the following rules when writing code, making technical decisions, or generating documentation for this project.

## 1. Zero Fabrication Policy
- **No Fabricated Material Values:** You must NEVER invent thermophysical properties (conductivity, density, specific heat, etc.). All material properties must come from established sources (ASHRAE, BIS, ISO, published research) or be clearly marked as user-defined.
- **No Fabricated Weather Data:** You must NEVER invent weather data. Weather data must come from real EPW files, the NASA POWER API, or explicit user CSV uploads.
- **No Fabricated Simulation Results:** You must NEVER generate mock thermal simulation results (like temperature graphs or energy use values) and present them as real outputs.
- **No Fabricated Validation Metrics:** When running ASHRAE Standard 140 (BESTEST) validations, you must present the exact results generated by the engine. You must not invent or fudge validation metrics to pass tests.

## 2. Test Data vs. Real Data
- Test data used in unit tests or mock UI states must be clearly and visibly marked as "TEST DATA" or "MOCK".
- Test data must NEVER be presented to the end user as real engineering data.

## 3. Engineering Decisions and Assumptions
- **No Silent Assumptions:** You must NEVER silently make major engineering or physical assumptions to simplify a problem or bypass a blocker.
- **Explicit Documentation:** For every major engineering decision you make, you must document it in `docs/ASSUMPTIONS.md`. You must state:
  1. The assumption.
  2. Why it was made.
  3. Its limitations.

## 4. Architectural Boundaries
- **Engine Agnosticism:** Do NOT couple the `ShelterModel` domain directly to EnergyPlus internals. The domain model must remain abstract and capable of targeting EnergyPlus, OpenStudio, or ANSYS.
- **Frontend Isolation:** Do NOT couple frontend logic (React/Next.js) directly to EnergyPlus internals, IDF formats, or engine-specific idiosyncrasies. The frontend must only speak to the backend using standard API DTOs.
- **Modularity:** Maintain strict separation of concerns across the 4-layer backend architecture (API → Schema → Service → Engine).

## 5. Explicit Optimization
- Optimization objectives must ALWAYS be explicit.
- The word "best" must always be qualified: "best" means the optimal solution *under the defined objectives and constraints* (e.g., "best" for comfort hours vs. "best" for heating demand).
